        DOORWAY
        Computer Use PRD
        Advanced visible automation layer for terminal, browser, desktop app, and multi-agent workflows
              Purpose of this document
              This is the sixth Doorway document. It does not replace the Main PRD, Core Flow Brief, Technical PRD, GOAT Features PRD, or Master Handoff PRD. It specifies the optional advanced Computer Use layer: how Doorway can safely observe, control, verify, and replay real computer interactions while keeping the user in charge.

        1. Executive Summary
        Doorway already has five major specifications: product vision, core flow, technical architecture, GOAT differentiation, and the master handoff. This document adds one missing advanced layer: computer use. Computer use means Doorway can observe and control real computer surfaces - terminals, browsers, local applications, simulators, dev servers, editors, and remote environments - while preserving visibility, auditability, worktree isolation, and user approval.
        The product goal is not to make a hidden bot that silently drives a machine. The product goal is to create the best visible supervision layer for AI-assisted software work: an agent can open a browser preview, click through a UI, reproduce a bug, run a test, inspect logs, operate a simulator, and report back into the same Doorway thread. The user can pause, correct, replay, approve, reject, or take over at any time.
              Main strategic decision
              Doorway should not begin with full raw OS mouse/keyboard control. V1 should begin with structured surfaces: terminal buffers, browser DOM/accessibility trees, Playwright/CDP, file watchers, git diffs, and app logs. Raw screenshot + cursor control should be the fallback path, not the default path.

        2. Research Findings: What Advanced Users Now Expect
        Current agentic coding products are moving from one-chat assistance toward supervised fleets of agents. The most relevant market signals are:
        a unified workspace for agents, local/cloud handoff, multi-workspace layout, agent sidebar, diffs, PR workflow, integrated browser, and marketplace plugins.
        parallel threads, worktrees, local/worktree/cloud modes, integrated terminals, computer use for macOS apps, in-app browser, automations, thread continuity, memory, plugins, SSH/devboxes, and richer review surfaces.
        terminal-first coding plus emerging computer-control workflows for macOS where Claude can operate files, browsers, apps, and development tools with permission gates.
        validation that developers want local worktree-based orchestration of multiple CLI agents, visible terminals, diff review, and editor handoff.
        browser and GUI agents remain unreliable under UI variation and prompt injection. Strong products need human-in-the-loop correction, deterministic policies, provenance, sandboxing, and structured observations rather than only pixels.
              Market pattern
              Implication for Doorway Computer Use
              Agent windows and sidebars
              Doorway must make running agents visible, searchable, pausable, and resumable.
              Worktrees as default isolation
              Computer-use actions must bind to a worktree/session, not a vague global machine state.
              Integrated browser / local preview
              Doorway needs first-class browser observation and annotation for frontend work.
              Computer use in background
              Doorway can support background desktops/VMs later, but V1 should prioritize visible local supervision.
              Automations and recurring threads
              Doorway should let the same thread wake up, inspect state, run checks, and report.
              Prompt injection risk
              Doorway must separate trusted user intent from untrusted page/app content.
              Senior developer workflow
              Review, test, merge, rollback, and proofs matter more than raw autonomous clicking.
        3. Product Thesis and Non-Negotiables
        Doorway Computer Use should be built as a control plane for supervised autonomy. It should make AI agents better at using the developer&#x2019;s computer while avoiding the chaos of blind automation. The user should feel that Doorway is a calm command center, not a risky bot taking over the machine.
              Non-negotiable
              Specification
              Visible by default
              The user can always see the terminal/browser/app being controlled or can open the live view in one click.
              Doorway-owned ledger
              Every action is stored in the Doorway thread ledger with timestamp, surface, reason, risk level, before/after observation, and result.
              Semantic before visual
              Prefer terminal buffer, DOM tree, accessibility tree, filesystem state, and logs before relying on screenshot/OCR.
              Least privilege
              Each agent gets the minimum surface access required: project worktree, browser profile, terminal pane, or app window.
              Approval gates
              Destructive, external, financial, account, network, secret, email, and production actions require explicit user approval.
              Replayability
              Any meaningful run should produce a replay: prompt, plan, observations, actions, outputs, diffs, screenshots, and decisions.
              Human takeover
              User can pause, abort, resume, edit the plan, inject instructions, or take over mouse/keyboard.
              No provider dependency
              Computer-use runtime works with Doorway Harness and any supported agent; it is not tied to one model/provider.
              Positioning
              Doorway Computer Use is not &#x201C;AI controls your computer blindly.&#x201D; It is &#x201C;AI operates scoped surfaces while Doorway records, constrains, verifies, and lets the user supervise every consequential move.&#x201D;
        4. Doorway Computer Use Layer: System Model
        The computer-use layer attaches to the existing Doorway architecture. It does not replace the terminal/worktree system. It expands Doorway from &#x201C;visible terminal cockpit&#x201D; to &#x201C;visible computer cockpit.&#x201D;
        Doorway GUI
              Component
              Responsibility
              Computer Use Supervisor
              Coordinates observe-plan-act-verify loops and chooses the safest surface adapter.
              Observation Engine
              Collects screenshots, terminal buffers, DOM/accessibility trees, app metadata, logs, files, git status, and network traces.
              Action Engine
              Executes typed actions: terminal input, browser click/fill/navigation, app click/type, file open, drag/drop, hotkey, wait, screenshot.
              Policy Engine
              Scores action risk, blocks disallowed actions, requires approvals, masks secrets, and limits scope.
              Verification Engine
              Checks whether the action achieved the goal using state changes, DOM, tests, files, screenshots, and app logs.
              Replay Recorder
              Stores action timeline, before/after observations, screenshots, summaries, diffs, and permission receipts.
              Surface Adapters
              Terminal, Browser, Desktop App, IDE, Simulator, Remote Desktop, and future mobile/device adapters.
        5. Core User Flows
        Flow A: Frontend bug reproduction and fix
        User asks: &#x201C;Reproduce the checkout modal bug, fix it, and verify in browser.&#x201D;
        Doorway creates or selects a worktree and launches the selected coding agent.
        Doorway starts the dev server in a visible terminal and opens a browser preview.
        Computer Use Supervisor observes the page through DOM/accessibility tree + screenshot.
        Agent clicks through the UI with approval-free low-risk actions inside the local preview.
        Doorway records the failing state, console logs, network errors, and screenshot.
        Coding agent edits files; Doorway shows live diff.
        Supervisor re-runs the browser flow and verifies the bug is gone.
        Doorway presents proof: before/after screenshot, test result, changed files, and replay.
        Flow B: Multi-agent UI implementation race
        User asks for a new settings page with polished UI.
        Doorway launches two worktree agents: one Codex implementation, one Claude/OpenCode implementation.
        Each agent runs its own dev server/browser preview in isolated ports.
        Computer Use Supervisor captures screenshots and interaction paths for each candidate.
        Reviewer agent compares UI, accessibility, test status, diff size, and risk.
        User chooses winner or merges parts; Doorway opens PR/commit path.
        Flow C: Desktop app testing
        User says: &#x201C;Test the Electron settings window and fix the broken save button.&#x201D;
        Doorway launches the local app in a scoped environment.
        Observation uses accessibility tree/window metadata first; screenshot fallback second.
        Actions click controls, type test values, and watch local logs.
        Agent edits code, rebuilds, relaunches, and verifies the save flow.
        Doorway records UI trajectory and links it to the final diff.
        Flow D: External service workflow with strict approvals
        User asks: &#x201C;Create a GitHub PR and address review comments.&#x201D;
        Doorway prefers GitHub CLI/API/MCP over browser clicking.
        If browser UI is necessary, it opens a logged-in browser profile but gates every state-changing action.
        Before commenting, merging, closing, emailing, or changing remote state, Doorway asks approval with a short permission receipt.
        After action, Doorway verifies remote status and logs the result.
        6. Feature Requirements
        6.1 Surface dashboard
        Live cards for every controlled surface: terminal, browser, app, simulator, remote desktop, test runner.
        Each card shows status, current action, risk level, last observation, owner agent, worktree, and pause/kill buttons.
        Cards can expand into raw view: terminal stream, browser preview, screenshot timeline, logs, DOM/accessibility snapshot.
        6.2 Browser workbench
        Open a local dev server, website, or file-backed page in an isolated browser profile.
        Capture DOM, accessibility tree, screenshot, console logs, network requests, storage state, and selected elements.
        Let user comment on the page: &#x201C;fix this spacing,&#x201D; &#x201C;this button is wrong,&#x201D; &#x201C;click here and test checkout.&#x201D;
        Allow agent to perform low-risk local actions automatically; gate external or authenticated actions.
        6.3 Desktop app workbench
        Attach to a user-approved app window or launch an app from a worktree command.
        Observe using accessibility APIs when available; use screenshot/vision fallback only when needed.
        Execute click, type, hotkey, menu, drag/drop, wait, screenshot, focus, and open-file actions.
        Record every action with before/after observation and verification result.
        6.4 Terminal + app hybrid loops
        Let a coding agent read terminal failures and then operate the browser/app to verify changes.
        Terminal commands and GUI actions share one Doorway thread timeline.
        The agent can say &#x201C;tests passed but browser still fails,&#x201D; and Doorway shows both proofs.
        6.5 Computer-use replay
        Store action trajectories as deterministic-ish scripts: observations, target descriptors, action primitives, waits, and assertions.
        Replay a flow after code changes to verify regressions.
        Export replay as Playwright test when it is browser-based; export as markdown/video for desktop app flows.
        6.6 Permission receipts
        Before high-risk actions, Doorway shows: action, target, reason, expected outcome, blast radius, and rollback path.
        Receipts are stored in the session ledger.
        User can approve once, approve for session, deny, or modify scope.
        6.7 Human correction memory
        When user corrects the agent (&#x201C;wrong button,&#x201D; &#x201C;do not touch prod,&#x201D; &#x201C;use staging profile&#x201D;), Doorway stores the correction as scoped memory.
        Corrections become future harness constraints, not random chat history noise.
        Project-level rules can be promoted to AGENTS.md/DOORWAY.md recommendations.
        6.8 Multi-surface best-of-N
        Run the same UI task across multiple worktrees and browser previews.
        Compare screenshots, test results, accessibility checks, diff quality, and reviewer score.
        Let user pick the best implementation with visible proof.
        7. Technical Architecture
        The technical rule: isolate execution, structure observations, and make every consequential action auditable.

              Recommended stack

              Keeps continuity with existing Doorway PRDs while allowing native automation modules.
              Terminal control
              tmux on macOS/Linux/WSL; node-pty/ConPTY fallback; external terminal attach mode
              Visible terminal orchestration remains the foundation.
              Browser control
              Playwright + CDP + isolated persistent browser profiles; optional MCP browser server

              Requires explicit user-granted permissions.
              Desktop control Windows

              Phased after V1.
              Desktop control Linux
              AT-SPI, xdotool/wtype where available, Wayland portal constraints, Xvfb/noVNC for sandboxed sessions
              Best for controlled dev environments.
              State store
              SQLite + append-only event log + blob store for screenshots/videos + git metadata
              Doorway ledger is canonical.
              Verification
              Playwright assertions, DOM checks, log scans, test outputs, visual snapshots, LLM verifier only after deterministic checks
              Do not trust model self-report alone.
              Sandboxing
              Worktrees, browser profiles, local users, containers/VMs, network allowlists, permissions policy
              Different risk tiers get different isolation.
              Observability
              OpenTelemetry-compatible spans, action IDs, terminal/browsing/app traces, crash reporting opt-in
              Must be local-first and privacy-respecting.
        Core runtime loop:
        1. Observe current surface state.
        2. Compile trusted task + current state + policy constraints.
        3. Ask Doorway Harness or selected agent for next action plan.
        4. Policy Engine scores proposed action.
        5. If safe: execute; if risky: request approval.
        6. Capture before/after state.
        7. Verify progress against objective.
        8. Append action event to Doorway ledger.
        9. Continue, pause, escalate, or finish with proof.

        9. Safety, Security, and Trust Model
        Computer use creates a bigger attack surface than terminal-only orchestration. Doorway must treat web pages, emails, documents, screenshots, logs, and external app content as untrusted by default. The agent must never treat untrusted content as higher priority than the user&#x2019;s goal or Doorway policy.
              Risk class
              Examples
              Doorway behavior
              Low
              Click local preview, inspect page, type into local dev form, scroll, take screenshot
              Allowed in scoped session; logged.
              Medium
              Install dependency, run test that accesses network, modify many files, change app settings
              May require session-level approval; logged with reason.
              High
              Email/post/comment/push/merge/delete files outside worktree, access secrets, production API calls
              Explicit one-time approval with permission receipt.
              Critical
              Financial transactions, credential export, destructive cloud actions, public releases, prod database mutations
              Default blocked or multi-step approval with dry-run and rollback path.
        9.1 Prompt injection defense
        Separate trusted user/developer instructions from untrusted page/app/document content in the context compiler.
        Mark every observation with provenance: user, local code, remote page, terminal output, document, external app, model output.
        For any state-changing action, require a justification chain grounded in trusted user intent and current observed state.
        Never let web page text or document text grant new permissions.
        9.2 Secret and account protection
        Mask environment variables, tokens, cookies, credentials, SSH keys, and secret files in observations unless explicitly approved.
        Use separate browser profiles for agent sessions; prefer logged-out or staging accounts for external websites.
        Block copy/paste of secrets into untrusted pages by default.
        Warn when a surface is logged into a sensitive account.
        9.3 Tamper-evident logging
        Append-only action events with action ID, actor, surface, before/after hash, and timestamp.
        Permission receipts cannot be edited silently; edits create new events.
        Replay artifacts can be shared with redaction.
        9.4 Scoped agent identities
        Every agent has a scope: worktree, browser profile, app window, terminal pane, and network policy.
        Agents cannot freely jump surfaces unless Doorway grants a surface token.
        Surface tokens expire when the task ends or user revokes access.
        10. Reliability Engineering
        The biggest product risk is not that Doorway cannot click. The biggest risk is that it clicks the wrong thing, loops forever, misreads state, or claims success without proof. Reliability must be engineered as a first-class feature.
              Failure mode
              Mitigation
              Wrong target click
              Use semantic target descriptors first; require target confidence; show hover preview for medium/high-risk actions.
              UI changed during action
              Re-observe immediately before execution; cancel if target moved or semantic identity changed.
              Agent loop
              Iteration budget, no-progress detector, repeated-action detector, escalate to user after threshold.
              False success claim
              Require deterministic verification: tests, DOM assertion, file diff, status code, screenshot comparison, or log evidence.
              Environment drift
              Session setup scripts, worktree manifests, dependency cache, port allocator, environment health checks.
              Crash or app restart
              Persist session ledger after every action; replay can reconstruct open surfaces and continue.
              Network flakiness
              Retry only idempotent observations; do not retry state-changing actions without confirmation.
              Cross-agent interference
              Worktrees, separate browser profiles, separate ports, surface locks, file ownership hints.
              Doorway proof requirement
              A task is not &#x201C;done&#x201D; because the agent says it is done. A task is done when Doorway can show proof: passing tests, verified UI path, changed files, screenshots, logs, and a reviewable diff.

        11.1 The &#x201C;Fix while watching&#x201D; experience
        User opens a local app/browser inside Doorway.
        User highlights or comments on the broken area.
        Doorway turns the annotation into structured context for the coding agent.
        Agent edits code while Computer Use Supervisor keeps the app/browser open.
        Doorway verifies the fix in the same UI surface.

        Advanced/future mode: each agent gets an isolated desktop or browser VM.

        14. Engineering Handoff Prompt

        Appendix A: Explicit Non-Goals
        Do not build hidden provider-bypass behavior into computer use.
        Do not silently operate sensitive accounts or production systems.
        Do not rely on brittle config/database mutation of external tools as a core product strategy.
        Do not make screenshot OCR the primary observation method when structured state is available.
        Do not claim autonomous completion without reproducible proof.
        Do not allow untrusted webpage/app content to create new permissions or override user intent.
