        1. Executive Summary
        Doorway
              Problem
              AI coding agents are becoming powerful, but the developer experience is fragmented. Terminal agents are trusted but messy. IDE agents are polished but closed. Cloud agents are convenient but opaque. Teams need a clean way to run multiple agents, see exactly what they did, review diffs, and merge only the best work.
              Solution
              Doorway provides a premium GUI over real CLI agents: it launches visible terminals, creates isolated git worktrees, streams agent activity into a structured timeline, watches file changes, runs tests, summarizes progress, and gives a final review/merge board.
              Dimension
              Decision
              Primary workflow
              User submits one task, Doorway creates agent runs in isolated worktrees, agents work in visible terminals, user reviews and merges.
              Primary backend
              Local orchestrator with terminal sessions, git worktrees, file watcher, SQLite session store, and adapter plugins.
              Primary UI inspiration
              Cursor 3 agent workspace + Codex app parallel threads/worktrees + Conductor-style parallel agent review, but terminal-native.
              Core moat
              Visible multi-agent orchestration, review/merge quality, adapter ecosystem, local-first trust, and beautiful UX.
              Open-source boundary
              Core app and adapters are open source; optional hosted/team features can be commercial later.
        1.1 Non-goals
        Doorway is not an attempt to bypass provider billing, access controls, or product boundaries.
        Doorway does not need to become a full operating system; it is a focused developer cockpit.
        Doorway should not require users to abandon their existing editors or terminals.
        Doorway should not depend on one proprietary model or one provider-specific SDK.
        2. Product Vision and Name
        Working name: Doorway.
              Why Doorway works
              The name is simple, human, memorable, and not AI-slop. It suggests entry, access, transition, and a clean passage between the developer and a team of agents. It does not sound like a crypto protocol or military AI system.
        2.1 Vision Statement
        Doorway is the place where a developer turns one intention into a controlled team of visible agent runs, then reviews the resulting code like a senior engineer.
        2.2 Product Narrative
        Today a developer either uses a terminal agent directly and loses structure, or uses a polished IDE agent and loses visibility. Doorway combines the two: real terminals, real files, real diffs, real review, wrapped in a modern agent workspace.

        3. Market and Benchmark Analysis
        Doorway should compete at the experience level with modern agent-first coding tools. It should learn from Cursor 3, the Codex app, Windsurf-style agent flows, and Conductor-style parallel agent workspaces without cloning their private implementation or visual assets.
              Benchmark
              Observed direction
              Doorway response
              Cursor 3
              Agent-first workspace: natural-language task input, agent sidebar, multi-repo/workspace direction, local/cloud continuity [S1].
              Build an agent dashboard where task cards, runs, terminals, diffs, and merge state are first-class.
              Codex app
              Focused desktop app for parallel Codex threads, worktree support, automations, Git review, local environments, and app-server style integrations [S5-S12].
              Use git worktrees as the core execution primitive; add review/merge board and terminal-aware session model.
              Conductor-style products
              Parallel agent workspaces with review and merge UX.
              Open-source the terminal-native version with adapters for multiple CLI agents.
              Traditional terminal agents
              Trusted raw execution but poor organization, no central review, and hard-to-follow logs.
              Keep raw terminal visible but add structured timeline, diff intelligence, and task state.
              IDE agents
              Beautiful inline editing but often closed or tied to one runtime.
              Make Doorway editor-agnostic and agent-agnostic; integrate with existing editors later.
        3.1 Strategic Gap
              Gap to exploit
              There is room for an open-source, local-first, terminal-native agent cockpit that feels as polished as Cursor/Codex but is built around visible execution, worktree isolation, and adapter freedom.

        5. Product Principles
              Principle
              Meaning in product
              Visible by default
              Every agent run should be inspectable through a terminal, transcript, diff, and event timeline.
              Local-first trust
              The first version runs on the user machine and stores sessions locally.
              Worktrees over chaos
              Every meaningful agent run happens in an isolated branch/worktree unless the user explicitly chooses direct edit mode.
              Review before merge
              Doorway never hides code changes; all agent output goes through review.
              Provider-agnostic
              Claude Code, Codex, OpenCode, Aider, and custom agents are adapters, not the product identity.
              Beautiful but honest
              The UI can be premium, but raw terminals and logs remain one click away.
              Composable
              Agents, skills, prompts, commands, and memories are small reusable building blocks.
        6. Core User Experience
        6.1 Primary Flow
        User opens Doorway and selects a project folder.
        Doorway detects git state, package manager, framework, scripts, test commands, and existing instructions.
        User writes a task in the command composer and optionally attaches images/files.
        Doorway proposes a task plan: roles, agents, worktrees, tests, and risk level.
        User clicks Launch.
        Doorway creates worktrees and starts visible terminal sessions.
        Agents work in parallel; Doorway streams terminal output into a structured timeline.
        Doorway watches file changes, diffs, and tests.
        When runs finish, Doorway shows a review board with diffs, test results, conflicts, and merge recommendations.
        User accepts, rejects, re-runs, or merges changes into an integration branch/main branch.

        Doorway-level subagents are independent terminal sessions with role-specific prompts, isolated worktrees, and shared task context. Native subagent systems inside individual tools can also be supported through adapters, but Doorway should not depend on them.

        8.3 Scheduler Rules
        Never run two write-capable agents in the same worktree by default.
        Agents with independent scopes can run in parallel.
        Reviewer waits for implementation runs or can perform early review on partial diffs.
        Tester can either run in its own worktree or run against an integration branch after merge simulation.

        Show changed files per agent run.
        Show inline diff and side-by-side diff.
        Show test results and command logs linked to diffs.
        Detect overlapping edits across agent runs.
        Suggest merge order based on dependencies and conflicts.

        9.4 Conflict Strategy
              Conflict type
              Doorway behavior
              No conflict
              Fast merge into integration branch and run tests.
              Text conflict
              Show conflict file, launch Fixer agent in integration worktree, require user approval before final merge.
              Semantic conflict
              Tests fail after clean merge; launch Reviewer/Fixer with failing logs and relevant diffs.
              High-risk file
              Require explicit approval for package files, migrations, auth, secrets, CI, deployment configs.

        11. Terminal Runtime and Adapter Layer
        Doorway should support both embedded terminals and external visible terminals. The technical foundation is terminal control, not pixel scraping. node-pty provides pseudo-terminal process control [S14], xterm.js renders terminals in the UI [S15], and tmux control mode can manage external multi-pane sessions [S16].

        12.3 Interaction Quality Bar
        Launching a task should feel instant even if agent startup takes time; show staged progress.
        The user should never wonder where code was changed.
        Every agent run should have a visible stop button.
        Every merge should be reversible until user explicitly finalizes.
        Raw terminal should be one click away from every summarized event.
        Pasted images/files should be stored visibly in the task context and removable before launch.

        14. Non-Functional Requirements
              Category
              Requirement

              V1 targets macOS/Linux/WSL; Windows native support planned after terminal runtime stabilizes.

        15. Security, Trust, and Transparency
        Doorway must become trusted because it makes agent work visible and controllable. It should avoid dark patterns, hidden background execution, and ambiguous file access.
        15.1 Trust Model
        Every run has a visible command, working directory, branch, and terminal.
        The app shows exactly what context was sent to the agent.
        The app shows every file changed and every merge decision.
        User can pause/stop any run at any time.
        Potentially destructive commands and high-risk files can trigger approval warnings.
        Provider-specific usage must follow each provider/tool&#x2019;s documented terms and supported integration paths.
        15.2 Sensitive Path Policy
              Path/type
              Default behavior
              .env, keys, credentials
              Exclude from context and warn if modified.
              node_modules, build, dist
              Ignore from watcher by default.
              package lockfiles
              Allow but mark as package-impacting.
              migrations
              Mark high-risk; require review before merge.
              CI/deploy configs
              Mark high-risk; require review before merge.
              Auth/payment/security files
              Mark high-risk if detected by path heuristics.

        19. Risks and Mitigations
              Risk
              Impact
              Mitigation
              Terminal parsing is unreliable
              Bad statuses and confusing UI.
              Use file watcher/git as source of truth; support structured adapters where possible.
              Worktree complexity confuses users
              Merge mistakes.
              Hide complexity behind clear cards; always show branch/worktree details when expanded.
              Too many agents create chaos
              Poor output and high resource use.
              Default to 1-3 agents; require explicit launch for large plans.
              Provider-specific changes break adapters
              Runs fail.
              Adapter contract, capability checks, graceful degradation, provider-agnostic core.
              UI becomes too complex
              Users return to terminal.
              Opinionated defaults, progressive disclosure, strong information hierarchy.
              Windows terminal support is hard
              Limits adoption.
              Start with macOS/Linux/WSL; add ConPTY after core stabilizes.
              Open-source clones
              Competition.
              Move fast on quality, community, plugin ecosystem, design, and reliability.
        19.1 Brutal Founder Notes
        The app wins only if the first demo looks premium and obviously useful.
        Do not start with ten adapters. Start with one excellent adapter and one generic shell adapter.
        The review/merge board is more important than fancy chat animation.
        The terminal should feel like a source of trust, not a backend hack.
        The product must be useful even without any single proprietary agent.
